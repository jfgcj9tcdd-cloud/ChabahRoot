# ChabahRoot

ChabahRoot est une plateforme de télémétrie Linux centrée sur `tracefs`. Le projet capte des appels système jugés critiques, les transforme en événements normalisés, applique des règles comportementales, puis orchestre leur exploitation depuis une architecture volontairement simple à déployer et à auditer. Le choix de `tracefs` remplace ici l’ancienne piste eBPF afin d’éviter la compilation dépendante du noyau, de réduire le nombre de prérequis système et de garder une chaîne de traitement lisible en shell.

L’architecture repose sur cinq modules. `veille_kernel` est le point d’entrée au plus près du noyau : il vérifie la présence de `tracefs`, active les tracepoints `execve`, `setuid`, `setgid` et `prctl`, puis laisse un flux brut exploitable par le reste de la plateforme. `chaines_d_ecoute` assure la normalisation des lignes brutes ou des corpus hors ligne en NDJSON homogène, avec enrichissement minimal sur le contexte parent et filtrage élémentaire des mots sensibles. `vigie_comportementale` porte la détection, aussi bien sous forme de règles JSON évaluées par `jq` que sous forme de contrôles complémentaires orientés audit et surveillance défensive locale. `chambre_d_analyse` relie ces briques pour exécuter le pipeline complet sur une source vivante ou sur un fichier d’essai, et `socle_commun` fournit la journalisation et les garde-fous transverses dont les modules ont besoin pour rester cohérents.

Le fonctionnement attendu est direct. Sur une machine où `tracefs` est monté sous `/sys/kernel/tracing`, on commence par vérifier les prérequis du capteur avec `bash chabahroot/veille_kernel/check.sh`, de préférence avec les privilèges nécessaires. Une fois cette étape validée, `bash chabahroot/veille_kernel/orchestrator.sh start` active la capture noyau et alimente le fichier de relais utilisé par la suite du pipeline. Pour une chaîne complète hors ligne ou en phase de validation, `bash chabahroot/chambre_d_analyse/run_detection.sh --sample --pipeline-only` lit le corpus d’exemple, le normalise puis déclenche le moteur de règles. Si une source réelle ou un fichier externe doit être utilisé, la même commande accepte `--stdin` ou `--input <fichier>` sans changer les modules intermédiaires.

Les prérequis restent volontairement modestes. Il faut un noyau Linux exposant `tracefs` et les tracepoints système visés, ainsi que les outils `bash`, `jq`, `timeout`, `ps` et `find`. Les opérations qui écrivent dans `tracefs` exigent les privilèges root, mais la normalisation, l’évaluation des règles et les tests sur corpus peuvent être exécutés sans toucher au noyau, ce qui facilite les itérations de développement. Le dépôt contient d’ailleurs un scénario d’intégration simple dans `chambre_d_analyse/integration_tests.sh` afin de vérifier rapidement la syntaxe shell de tous les scripts maintenus et la traversée du pipeline d’exemple.

Le choix de `tracefs` structure tout le projet. La couche de capture écrit directement dans l’arborescence `/sys/kernel/tracing/events/.../enable`, en utilisant la forme de chemin correcte avec des séparateurs de répertoire plutôt qu’une notation à deux-points héritée d’anciens essais. Cette décision impose une discipline stricte sur la séparation entre journaux humains et données machine, car les modules enchaînent redirections, substitutions de commandes et pipes continus. Le nettoyage final du dépôt vise précisément cet objectif : une arborescence francisée sans doublons, un socle shell homogène, et une documentation alignée sur l’architecture effectivement exécutable.
